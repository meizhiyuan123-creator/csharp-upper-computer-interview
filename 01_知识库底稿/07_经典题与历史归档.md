## 1. 操作系统中死锁产生的四个必要条件是什么？上位机多线程编程中如何有效预防与克服死锁？

- **题目标识**：`CLASSIC-01`
- **重要程度**：⭐⭐⭐⭐ (4星)
- **核心标签**：`操作系统` `多线程` `死锁` `四大必要条件`

### 💡 30秒速记提纲（面试张口就来）
> 1. **死锁四大必要条件**：互斥条件、请求与保持条件、不剥夺条件、循环等待（环路等待）条件。
> 2. **核心破坏手段**：破坏“循环等待”最为有效——在代码中**严格固定锁的获取顺序**（例如总是先锁 A，再锁 B）；或者破坏“请求与保持”——使用带有超时的锁尝试（如 `Monitor.TryEnter(obj, timeout)` 或 `SemaphoreSlim.WaitAsync(timeout)`），超时未获取立即释放已持有的锁并回退重试。
> 3. **规避 UI 死锁**：禁止在 UI 主线程对异步 Task 调用 `.Result` 或 `.Wait()` 同步阻塞。

### 🔍 深入原理解析
### 1. 经典死锁代码模拟
线程 1 持有 LockA 试图获取 LockB；线程 2 持有 LockB 试图获取 LockA。两线程永久僵持。

### 2. 工控上位机死锁预防规范
1. **全局锁顺序规范**：如果涉及多个设备（如串口端口锁与电机状态锁），所有业务模块必须按照固定的全局等级制度依次加锁。
2. **采用超时重试机制**：使用 `await sema.WaitAsync(TimeSpan.FromSeconds(2))`，若超时抛出日志告警并释放资源，而不是无限挂起导致整机卡死。
3. **最小化锁范围**：不要在锁块内执行耗时的 I/O 操作、文件写入或调用不受控的外部回调。

### 🛠️ 上位机实战避坑（工程案例）
在多轴运动控制联动中，X 轴与 Y 轴拥有各自的硬件互斥锁。为防止插补计算与原点回归两组并发线程出现反向死锁，规定所有跨轴联动操作必须按“X轴 -> Y轴 -> Z轴”的字母表固定顺序申请资源，从数学逻辑上彻底斩断了形成环路等待的可能性。

### ⚠️ 常见连环追问
- Q: 银行家算法的基本原理是什么？（答：一种避免死锁的动态资源分配算法，在分配前试探分配后系统是否依然处于安全状态，若是才真正分配，否则让进程等待）

## 2. 进程（Process）与线程（Thread）的本质区别是什么？在 Windows 上位机环境下如何权衡？

- **题目标识**：`CLASSIC-02`
- **重要程度**：⭐⭐⭐ (3星)
- **核心标签**：`操作系统` `进程与线程` `内存模型`

### 💡 30秒速记提纲（面试张口就来）
> 1. **资源与调度**：进程是**操作系统资源分配的独立基本单位**（拥有独立的虚拟地址空间、句柄表、安全上下文）；线程是**CPU 调度与执行的基本单位**，同一进程内的所有线程共享该进程的地址空间和全局资源。
> 2. **开销差异**：进程创建和上下文切换开销大，崩溃时相互隔离互不影响；线程创建与切换轻量（通常只占用约 1MB 栈空间），但同一进程内某个线程如果发生访问违规（如 AccessViolationException）可能直接导致整个进程崩溃。
> 3. **上位机选型**：常规测控系统采用单进程多线程模型（高效通信与低延迟共享内存）；对于稳定性要求极高的高危硬件（如不稳定易崩溃的第三方驱动），通常采用**独立看门狗进程或跨进程架构**进行物理隔离保护。

### 🔍 深入原理解析
### 1. 深入对比
- **内存隔离**：进程间通信（IPC）必须通过命名管道（NamedPipe）、共享内存（MemoryMappedFile）或 Socket；线程间通信只需直接读写共享内存变量（需注意线程同步安全）。
- **异常隔离**：托管环境下的普通异常可用 try-catch 拦截，但如果是 C++ 原生 DLL 导致的硬崩溃，线程级崩溃会拖垮整个宿主上位机。

### 🛠️ 上位机实战避坑（工程案例）
在上位机系统中，主程序负责测控与 UI 显示；针对某老旧分析仪不稳定的第三方驱动，单独编写了一个无界面的 Console 辅助进程进行托管，二者通过命名管道进行高速二进制通信。即使第三方驱动偶发崩溃，主上位机不仅不会闪退，还能自动检测并拉起重启该辅助进程，实现了工业级的容灾弹性。

### ⚠️ 常见连环追问
- Q: 什么是纤程（Fiber）与协程？C# 的 async/await 和线程是什么关系？（答：async/await 是语言级协程/用户态调度，并不等同于创建新线程，是在少量线程池线程之间复用 CPU）

## 3. 方法重载（Overload）与方法重写（Override）的深层区别？C# new 隐藏父类方法的区别与危害？

- **题目标识**：`CLASSIC-03`
- **重要程度**：⭐⭐⭐ (3星)
- **核心标签**：`面向对象` `重载与重写` `虚方法` `多态`

### 💡 30秒速记提纲（面试张口就来）
> 1. **重载（Overload）**：编译期多态（早绑定），在同一类中，方法名相同但参数列表（个数、类型、顺序）不同，调用哪个版本在编译阶段即由静态类型确定。
> 2. **重写（Override）**：运行时多态（晚绑定），子类重写基类带 `virtual` 或 `abstract` 的方法，方法签名必须完全一致，通过对象的**虚方法表（vtable）**动态分派实际执行逻辑。
> 3. **new 隐藏的危害**：`new` 仅仅是隐藏基类方法（断开了虚方法分派链），若将子类实例赋值给基类变量，调用时执行的将是基类的旧逻辑而非子类的新逻辑，容易产生隐蔽的逻辑 Bug，上位机中应尽量避免，优先规范使用 `override`。

### 🔍 深入原理解析
### 1. 虚方法表（vtable）底层分派过程
- 每个包含虚方法的类在被加载时，CLR 会为其生成一个方法表（Method Table）。
- 类的每个对象实例头包含一个指向该方法表指针（TypeHandle）。
- 当执行 `baseRef.DoAction()` 时，CLR 先查对象头找到真实运行时类型的 Method Table，再按槽位偏移调用对应地址，因此无论变量声明是什么类型，执行的都是当前真实实例的派生方法。

### 2. 代码对比展示
```csharp
class Base { public virtual void Run() => Console.Write("Base"); }
class SubOverride : Base { public override void Run() => Console.Write("SubO"); }
class SubNew : Base { public new void Run() => Console.Write("SubN"); }

Base b1 = new SubOverride(); b1.Run(); // 输出 SubO (多态生效)
Base b2 = new SubNew();      b2.Run(); // 输出 Base (多态失效！容易踩坑)
```

### 🛠️ 上位机实战避坑（工程案例）
在硬件抽象层（HAL）设计中，定义了抽象基类 `DeviceControllerBase`，声明虚方法 `public virtual async Task InitializeAsync()`。不同硬件子类（如 `SerialMotorController` 和 `TcpMotorController`）统一使用 `override` 重写。上层业务以基类指针统一调度启动流程，完美发挥多态优势。

### ⚠️ 常见连环追问
- Q: 抽象类（abstract）和接口（interface）在多态设计上如何选择？（答：IS-A 强血缘关系且需共享部分通用实现时用抽象类；CAN-DO 能力契约或多实现多重继承时用接口）

## 4. TCP 与 UDP 协议的核心区别？工业测控场景下视频流、控制指令与传感器数据应如何选型？

- **题目标识**：`CLASSIC-04`
- **重要程度**：⭐⭐⭐ (3星)
- **核心标签**：`网络通信` `TCP与UDP` `三次握手` `工业应用选型`

### 💡 30秒速记提纲（面试张口就来）
> 1. **协议特性**：TCP 是面向连接、可靠、基于字节流的双向通信协议（有三次握手、确认重传、拥塞控制和滑动窗口）；UDP 是无连接、不可靠、面向数据报的轻量传输协议（无连接状态，尽最大努力交付）。
> 2. **工业选型策略**：
>    - **控制指令与参数配置**：必须选 **TCP**（或基于 TCP 的 Modbus-TCP / OPC UA），控制电机启停、调速绝对不允许丢包或乱序。
>    - **高帧率工业相机裸流 / 实时视频**：优先选 **UDP**（如工业千兆网相机标准 GigE Vision 基于 UDP 广播），即使偶发丢弃一个像素包也不可触发全局阻塞，保证画面低延迟。
>    - **高频传感器瞬态波形**：若数据量极大且注重实时性可采用 UDP，并在应用层做序号去重与校验。

### 🔍 深入原理解析
### 1. 核心对比表
| 特性 | TCP | UDP |
| :--- | :--- | :--- |
| **连接性** | 面向连接（三次握手建立，四次挥手断开） | 无连接（直接发包） |
| **可靠性** | 极高（超时重传、丢包重发、顺序保证） | 不保证送达，不保证顺序 |
| **传输方式** | 流式传输（Stream），存在粘包现象 | 报文传输（Datagram），保留完整边界 |
| **头部开销** | 至少 20 字节，状态机复杂 | 仅 8 字节，极简高速 |
| **传输延迟** | 遇丢包会等待重传（队头阻塞 Head-of-Line Blocking） | 延迟极低且平稳，无等待 |

### 🛠️ 上位机实战避坑（工程案例）
在 3 路工业相机测控系统中，千兆网相机取流底层基于 GigE Vision 协议（基于 UDP 构建），即使网络偶发闪烁也保证 120 FPS 采集不发生队头阻塞；而向 PLC 下发跑台速度设定值与安全互锁信号时，严格采用 TCP 上的 Modbus-TCP 协议，确保每一条关键指令都被确认识别。

### ⚠️ 常见连环追问
- Q: TCP 粘包问题在 UDP 中存在吗？（答：不存在！UDP 是面向报文的，操作系统会完整保留发送端的数据边界，每次 recvfrom 读到的就是一整个完整的数据报）

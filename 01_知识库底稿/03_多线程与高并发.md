## 1. System.Threading.Channels 与传统的 BlockingCollection / ConcurrentQueue 相比有什么优势？上位机高频采集的生产-消费模型如何落地？

- **题目标识**：`THR-01`
- **重要程度**：⭐⭐⭐⭐⭐ (5星)
- **核心标签**：`多线程` `Channel` `高频采集` `生产消费模型`

### 💡 30秒速记提纲（面试张口就来）
> 1. **定性**：`Channel<T>` 是 .NET Core 3.0+ 引入的高性能原生异步生产-消费管道，专为 `async/await` 异步生态设计。
> 2. **本质区别**：`BlockingCollection<T>` 的消费是基于线程阻塞（`Take()` 占用真实操作系统线程等待）；而 `Channel<T>` 的 `ReadAsync()` 是**纯异步等待，不占用任何线程**，并支持背压控制（Backpressure BoundedChannel）。
> 3. **上位机落地**：创建 `Channel.CreateBounded<FrameData>(new BoundedChannelOptions(100) { FullMode = BoundedChannelFullMode.DropOldest })`，传感器极速写入，后台单个 Task 异步拉取并落盘，既绝不阻塞采集，又限制了内存上限。

### 🔍 深入原理解析
### 1. 核心性能演进对比
- `ConcurrentQueue<T>`：无等待唤醒通知机制，消费者必须通过 `Thread.Sleep` 轮询或自旋，消耗无谓 CPU，或配合外部 `AutoResetEvent`，代码复杂。
- `BlockingCollection<T>`：内部封装并发集合与信号量，但其等待只能是同步阻塞线程（Thread Block）。如果有 20 个传感器通道，就需要 20 个物理线程常驻等待，资源浪费。
- `System.Threading.Channels`：基于值任务 `ValueTask` 优化，分配极少。当管道无数据时，`await reader.WaitToReadAsync()` 挂起状态机释放线程回线程池；数据到来瞬间被调度激活。

### 2. 背压模式（Backpressure）对工控稳定性的决定性意义
当系统遇到磁盘卡顿或外部压力时，无界队列会导致对象无限堆积最终 `OutOfMemoryException`。`BoundedChannel` 提供四种防爆仓策略：
- `Wait`：生产者异步等待空间；
- `DropOldest`：**上位机实时监控最爱**——主动丢弃最旧数据，确保界面始终反映最新的工况；
- `DropNewest` / `DropWrite`：保护历史数据不受冲击。

### 🛠️ 上位机实战避坑（工程案例）
在步态动力学测控系统中，足底接触传感器以 500Hz 频率上报压力矩阵。采用单生产者单消费者的 `Channel.CreateBounded<SensorPacket>(1000)`，开启 `SingleWriter = true, SingleReader = true` 极致无锁优化模式。采集线程只管往 Channel `TryWrite`，后台单一后台 Task `await foreach` 批量异步写入 SQLite，即使系统突发卡顿也不会丢掉最新关键时序特征。

### ⚠️ 常见连环追问
- Q: SingleWriter 和 SingleReader 设置为 true 有什么底层好处？（答：Channel 内部会切换为更加轻量高效的单线程无竞争队列实现，完全省去多线程争用时的锁与 CAS 开销）

## 2. async / await 底层实现机制是什么？状态机是如何工作的？上位机开发中为什么禁止 async void？

- **题目标识**：`THR-02`
- **重要程度**：⭐⭐⭐⭐⭐ (5星)
- **核心标签**：`多线程` `async/await` `状态机` `死锁防范`

### 💡 30秒速记提纲（面试张口就来）
> 1. **底层机制**：编译器在编译阶段将 async 方法改写为一个实现了 `IAsyncStateMachine` 接口的**结构体状态机**，把代码按照 await 拆分为多个断点状态分支（MoveNext）。
> 2. **执行流程**：遇到 await 时，先检查 Task 是否已完成；若未完成，调用 `awaiter.UnsafeOnCompleted` 挂载延续任务（Continuation），保存局部变量并立即向调用方返回未完成的 Task；任务完成后由回调触发 `MoveNext` 恢复执行后面的代码。
> 3. **禁止 async void 的铁律**：`async void` 方法抛出的异常无法被外部 `try-catch` 捕获，会直接逃逸到 `SynchronizationContext` 导致上位机进程无预警直接崩溃（Crash），且调用方无法对其 `await`，无法跟踪任务生命周期。

### 🔍 深入原理解析
### 1. 编译器生成的状态机关键逻辑
```csharp
// 伪代码示意
struct <MyMethodAsync>d__1 : IAsyncStateMachine {
    public int <>1__state;
    public AsyncTaskMethodBuilder <>t__builder;
    private TaskAwaiter <>u__1;

    public void MoveNext() {
        switch (<>1__state) {
            case 0: // 恢复状态
                goto Label_Resume;
        }
        // 第一段同步代码
        var awaiter = DoWorkAsync().GetAwaiter();
        if (!awaiter.IsCompleted) {
            <>1__state = 0;
            <>u__1 = awaiter;
            // 注册回调，释放当前线程
            <>t__builder.AwaitUnsafeOnCompleted(ref awaiter, ref this);
            return;
        }
    Label_Resume:
        // 第二段代码
    }
}
```

### 2. 上位机中 async void 的唯一合法场景
只有在 **WPF 顶层 UI 事件处理器**（如 `private async void BtnStart_Click(object sender, RoutedEventArgs e)`）中允许使用，因为事件签名的委托类型是 `void (object, RoutedEventArgs)`，此时必须在方法内部用完整的 `try-catch` 包裹住所有逻辑，记录错误日志并弹窗提醒，严禁异常漏出！

### 🛠️ 上位机实战避坑（工程案例）
在工业设备运行期间，上位机 7x24 小时无人值守。曾有工程师在设备断线重连后台方法中写了 `private async void ReconnectLoop()`，当现场网线被拔出抛出 `SocketException` 时，由于没有返回 Task 托管，该异常直接打穿全局未捕获异常管道导致整个上位机软件瞬间闪退，酿成生产事故。规范做法：必须返回 `async Task` 并由顶层统筹捕获与重试。

### ⚠️ 常见连环追问
- Q: ConfigureAwait(false) 的作用是什么？在上位机何时使用？（答：通知调度器在后续恢复时不强求返回原来的 SynchronizationContext，在编写底层驱动、通信库、算法运算等与 UI 无关的代码时应全部加上，避免不必要地切回 UI 线程造成线程饥饿）

## 3. C# 中 lock、Monitor、SemaphoreSlim、ReaderWriterLockSlim 的底层区别与工控选型场景？

- **题目标识**：`THR-03`
- **重要程度**：⭐⭐⭐⭐ (4星)
- **核心标签**：`多线程` `并发锁` `SemaphoreSlim` `ReaderWriterLockSlim`

### 💡 30秒速记提纲（面试张口就来）
> 1. **lock 与 Monitor**：`lock(obj)` 语法糖底层就是 `Monitor.Enter / Exit`，基于对象头的 SyncBlock 同步块，是**独占且支持重入**的内核/用户混合锁，**只能同步代码，绝对不能在内部 await**。
> 2. **SemaphoreSlim**：支持**异步等待**（`await WaitAsync()`）的轻量级信号量，专门用于限制并发访问资源数量（如限制同时只能有 1 个任务操作串口/Socket）。
> 3. **ReaderWriterLockSlim**：读写分离锁，允许多个线程并发读，独占写，适合上位机“高频读实时参数，低频写配置”的高并发场景。

### 🔍 深入原理解析
### 1. 关键差异对比矩阵
| 锁类型 | 是否支持 await | 是否支持递归重入 | 开销大小 | 核心适用场景 |
| :--- | :---: | :---: | :---: | :--- |
| **lock (Monitor)** | ❌ 严禁（会报编译错误） | ✅ 支持 | 小（混合锁，先自旋后阻塞） | 纯内存变量原子修改、同步代码块互斥 |
| **SemaphoreSlim** | ✅ 原生支持 `WaitAsync` | ❌ 不支持重入 | 较小 | 工业通信端口异步互斥（如串口发包）、异步流限流 |
| **ReaderWriterLockSlim** | ❌ 严禁 await | ✅ 可配置支持 | 较大 | 多通道并发采集：几百个线程读配置，1个线程写配置 |
| **Interlocked** | ❌ 硬件原子指令 | N/A | 极小（无锁 CAS） | 计数器统计、帧率累计、标志位无锁切换 |

### 🛠️ 上位机实战避坑（工程案例）
在上位机串口通信层：发送指令是 `async Task<byte[]> SendAsync()` 异步方法，由于内部需要 `await Task.Delay` 等待下位机应答，**绝对不能用 `lock`**，此时必须使用 `private readonly SemaphoreSlim _serialLock = new(1, 1);`，通过 `await _serialLock.WaitAsync(); try { ... } finally { _serialLock.Release(); }` 实现完美的异步串行化互斥。

### ⚠️ 常见连环追问
- Q: lock(this) 和 lock(typeof(MyClass)) 为什么是反模式？（答：this 和类型对象都可能被外部代码访问到，如果外部也 lock 了同一个对象，容易引发不可预知的全局死锁，必须使用 private readonly object _locker = new();）

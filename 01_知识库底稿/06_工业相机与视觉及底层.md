## 1. 工业相机（如海康 SDK）在高帧率采集（如 120 FPS）场景下，如何设计多线程架构以避免内存剧烈抖动与丢帧？

- **题目标识**：`VIS-01`
- **重要程度**：⭐⭐⭐⭐⭐ (5星)
- **核心标签**：`视觉` `海康相机SDK` `高帧率取流` `多线程解耦`

### 💡 30秒速记提纲（面试张口就来）
> 1. **三大瓶颈**：高帧率下的回调线程阻塞导致 SDK 驱动底层丢帧、频繁在托管堆分配图像 Buffer 导致频繁 GC、以及 UI 主线程来不及渲染导致消息队列雪崩。
> 2. **三级解耦架构**：
>    - **第一级（硬件采集）**：使用 SDK 的回调函数或原生独立后台轮询线程（`MV_CC_GetOneFrameTimeout`），仅负责将裸图像指针数据快速推入预分配的环形无锁缓冲队列（RingBuffer），耗时控制在 1ms 内。
>    - **第二级（算法处理与录像落盘）**：后台专用计算 Task 从队列取出图像，直接在指针或共享内存上调用 OpenCvSharp 做算法分析，并异步送入视频压缩编码器（如 FFmpeg/OpenCV VideoWriter）。
>    - **第三级（UI 预览）**：采用 `WriteableBitmap` 结合定时器以 30 FPS 降频抽帧渲染，彻底与 120 FPS 物理采集脱钩。

### 🔍 深入原理解析
### 1. 内存池技术防抖动
严禁在相机每帧到来时 `new byte[width * height * 3]`！在 120 FPS 下，1080P RGB 图像每秒产生近 1GB 内存垃圾。工程解决方案：
- 初始化时申请固定容量的内存池（例如循环复用 10 个固定数组缓冲区）。
- 相机数据直接 `Buffer.BlockCopy` 或 `Marshal.Copy` 写入租借的缓冲区中，处理完毕后归还池中，全程零托管内存分配。

### 🛠️ 上位机实战避坑（工程案例）
在智能步态动力学测控系统中，搭载 3 路高速工业相机同步 120 FPS 采集。早期版本在相机回调里直接转 Bitmap 赋给 WPF 界面，导致 CPU 占用率 90% 且每 10 秒丢 5 帧。重构后：独立封装海康 SDK 采集管线，后台线程通过固定预分配内存缓冲队列接流，录像落盘走异步后台线程写入 NVMe SSD，WPF 端基于 WriteableBitmap 做 30Hz 抽帧同步预览，最终实现连续 3 小时录制 0 丢帧，CPU 占用稳定在 20% 以下。

### ⚠️ 常见连环追问
- Q: 软触发（Software Trigger）与硬外触发（Hardware External Trigger）有何区别？（答：软触发通过上位机下发指令，受网络与系统调度延迟影响有几毫秒抖动；硬触发通过传感器光电信号接相机 GPIO 引脚，纳秒/微秒级响应，多相机高精度同步必须使用硬外触发）

## 2. C# P/Invoke 调用 C/C++ 原生动态库（DLL）时，结构体对齐（Pack）、指针传递（IntPtr）与字符串封送的核心规则是什么？

- **题目标识**：`VIS-02`
- **重要程度**：⭐⭐⭐⭐ (4星)
- **核心标签**：`底层` `P/Invoke` `C++交互` `结构体封送与内存对齐`

### 💡 30秒速记提纲（面试张口就来）
> 1. **定性**：P/Invoke（Platform Invoke）是 CLR 提供的跨语言互操作机制，通过 Marshaler（封送拆构器）在托管世界与非托管世界之间转换数据类型。
> 2. **结构体传递黄金法则**：必须打上 `[StructLayout(LayoutKind.Sequential, Pack = 1 或 4)]` 特性，保证字段在内存中的偏移与 C/C++ 结构体严格字节对齐，否则字段错位读取必错。
> 3. **指针与内存管理铁律**：
>    - 传递数组或大块内存时使用 `IntPtr`；
>    - 若在托管代码中将托管数组地址传给 C++ 长时间使用，必须使用 `GCHandle.Alloc(array, GCHandleType.Pinned)` 固定内存钉住（Pin），防止 GC 在压缩内存时搬动该对象导致 C++ 产生野指针崩溃！

### 🔍 深入原理解析
### 1. 结构体封送对齐典型示范
```csharp
// C++ 结构体
// struct DevConfig { int id; char code[16]; double threshold; };

[StructLayout(LayoutKind.Sequential, Pack = 1, CharSet = CharSet.Ansi)]
public struct DevConfig {
    public int Id;
    [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 16)]
    public string Code;
    public double Threshold;
}
```

### 2. 回调函数互操作注意事项
如果将 C# 委托传给 C++ 作为事件回调函数：
- 必须在 C# 侧使用类成员字段持有该委托实例的强引用！
- 否则委托容易被 GC 当作无人引用的垃圾悄悄回收，导致 C++ 稍后调用该函数指针时抛出著名的 `ExecutionEngineException` 导致程序硬崩溃。

### 🛠️ 上位机实战避坑（工程案例）
在上位机与硬件加密狗及工业算法 C++ DLL 交互中：通过 `[DllImport("HardwareDog.dll", CallingConvention = CallingConvention.Cdecl)]` 调用原生接口。严格指定结构体 `Pack = 1` 并在数据传输完毕后显式通过 `Marshal.FreeHGlobal` 释放申请的非托管内存，杜绝了底层句柄与内存泄露风险。

### ⚠️ 常见连环追问
- Q: CallingConvention.Cdecl 与 StdCall 有什么区别？（答：Cdecl 由调用者清理栈，支持可变参数，C/C++默认；StdCall 由被调用者清理栈，Windows API常用，若约定不匹配会导致调用堆栈不平衡崩溃）

## 3. OpenCvSharp 图像处理（如 HSV 分割、连通域分析）中，如何高效将 Mat 转为 WPF 界面显示而不发生内存泄漏？

- **题目标识**：`VIS-03`
- **重要程度**：⭐⭐⭐⭐ (4星)
- **核心标签**：`视觉` `OpenCvSharp` `Mat转换` `内存泄漏`

### 💡 30秒速记提纲（面试张口就来）
> 1. **Mat 的本质**：`OpenCvSharp.Mat` 内部持有的是 C++ 堆上的原生非托管图像矩阵指针，**不受 C# GC 自动回收控制**，必须在使用完毕后显式调用 `mat.Dispose()`，否则分分钟造成非托管内存暴涨。
> 2. **转换效率陷阱**：严禁使用 `mat.ToBitmapSource()` 传统方式频繁创建新的图像源，该方法内部会重新申请内存并深拷贝，高频下直接触发卡顿。
> 3. **极致性能方案**：通过预先分配的 `WriteableBitmap`，直接获取其 `BackBuffer` 指针，使用 OpenCV 的 `mat.CopyTo` 或 `Buffer.MemoryCopy` 拷贝进显存脏区，或者使用 `OpenCvSharp.WpfExtensions` 的高效写入接口。

### 🔍 深入原理解析
### 1. 典型的 Mat 内存泄漏诱发
```csharp
// 错误示范：在高频循坏中链式调用未释放中间临时 Mat
var result = srcMat.CvtColor(ColorConversionCodes.BGR2HSV)
                   .InRange(lower, upper) // 这里产生的临时 Mat 永远没被释放！
                   .FindContours(...);
```
规范写法：中间产物必须用 `using var hsv = new Mat();` 或显式复用预先分配好的全局 Mat。

### 2. 高效转 WriteableBitmap 代码
```csharp
public void UpdateWpfImage(Mat mat, WriteableBitmap wpfBmp) {
    wpfBmp.Lock();
    // 确保分辨率和通道匹配（如 Bgr24）
    unsafe {
        Buffer.MemoryCopy(mat.DataPointer, wpfBmp.BackBuffer.ToPointer(), 
                          mat.Total() * mat.ElemSize(), mat.Total() * mat.ElemSize());
    }
    wpfBmp.AddDirtyRect(new Int32Rect(0, 0, mat.Width, mat.Height));
    wpfBmp.Unlock();
}
```

### 🛠️ 上位机实战避坑（工程案例）
在小动物步态接触面分析中：采集到的侧视与底视灰度图像经 HSV 动态分割和形态学闭运算提取足底轮廓。通过复用两个全局工作 `Mat` 缓冲区进行连通域分析（`ConnectedComponentsWithStats`），消除了中间临时对象的反复分配，足印实时跟踪分析耗时稳定在 4ms 以内，满足 120 FPS 准实时分析要求。

### ⚠️ 常见连环追问
- Q: OpenCvSharp 中的 using 语句块在循环中大量出现会导致性能变慢吗？（答：不会，using 编译后是 try-finally 调用 Dispose()，只是调用原生 cvReleaseImage 清理指针，比等待 GC 回收高效得多）

## 4. 工业相机硬件抽象层（HAL）设计：如何优雅封装海康、大华等不同品牌 SDK 并实现上层业务无缝平滑切换？

- **题目标识**：`VIS-04`
- **重要程度**：⭐⭐⭐⭐⭐ (5星)
- **核心标签**：`工业相机` `硬件抽象层` `HAL` `SDK封装` `海康与大华`

### 💡 30秒速记提纲（面试张口就来）
> 1. **定性**：遵循依赖倒置原则（DIP）与面向接口编程，在上层业务与底层厂商 SDK 之间构建统一的**硬件抽象层（HAL，Hardware Abstraction Layer）**。
> 2. **核心机制**：定义 `ICamera` 通用契约接口（曝光、增益、采流、触发、回调），统一输出不依赖厂商的原始帧数据模型（包含宽高、格式、非托管指针）；各品牌 SDK 编写适配器类实现该接口。
> 3. **无缝替换**：驱动内部消除厂商专有枚举（通过字典映射），错误码统一转译为自定义业务异常；通过依赖注入（DI）与工厂模式配置加载，实现换相机时上层业务代码 0 修改。

### 🔍 深入原理解析
### 1. 硬件抽象层（HAL）分层设计架构
```
[业务展示层 / ViewModel] -> 依赖抽象
       │
       ▼
[统一硬件抽象层 (HAL)] : ICamera 接口, CameraFrame 实体, CameraException 异常体系
       ▲                      ▲
       │ (实现)                │ (实现)
[海康驱动适配器 (HikDriver)]    [大华驱动适配器 (DahuaDriver)]
       │                      │
       ▼                      ▼
[海康原生 MvCamera SDK]        [大华原生 DaHua Camera SDK]
```

在三路工业相机测控项目中，当客户从海康千兆网工业相机更换为大华 USB3.0 相机时：由于整个系统严格依赖 `ICamera` 接口与统一的 `CameraFrameReceivedEventArgs`，开发人员仅需单独编写 `DahuaCameraDriver` 适配实现类并配置 DI 容器。上层的 HSV 动态分析算法、视频录像落盘以及 WriteableBitmap 渲染管线代码完全零修改，设备切换由原本预估的 2 周缩短为半天联调完成交付。

## 5. 多工业相机（如3台）同步采集时，如何实现微秒级硬件时间对齐与帧对齐数据结构设计？

- **题目标识**：`VIS-05`
- **重要程度**：⭐⭐⭐⭐⭐ (5星)
- **核心标签**：`多相机同步` `硬件触发` `主从级联` `帧对齐` `时间戳对齐`

### 💡 30秒速记提纲（面试张口就来）
> 1. **同步指标要求**：步态动力学在 120 FPS 下帧间隙仅 8.33ms，多视角空间 3D 重建要求相机间时间差必须小于 100 微秒，否则空间点出现几何畸变。
> 2. **硬件物理对齐**：采用 **TTL 硬件外触发主从级联**（主相机 Line2 输出 Strobe 脉冲，光耦隔离并联至从机 Line0 触发输入），或由外部信号源/PLC 发送 120Hz 脉冲硬触发，实现物理曝光微秒级同频同相。
> 3. **上位机帧对齐结构设计**：提取每路相机硬件生成的 `Hardware FrameID` 和 `Device Nanosecond Timestamp`。维护滑动时间窗字典 `ConcurrentDictionary<long, SynchronizedFrameGroup>`，当三路相机相同 FrameID 均就绪后打包投递给算法；若超时（如 20ms）未集齐则判定丢帧并告警。

### 🔍 深入原理解析
### 1. 硬件外触发走线拓扑
```
[高精度脉冲发生器 / 主相机 Line2 Strobe]
       │ (120Hz TTL 脉冲硬线并联)
       ├─────────────────┬─────────────────┐
       ▼                 ▼                 ▼
[相机1 Line0 Input] [相机2 Line0 Input] [相机3 Line0 Input]
   (左侧视视角)         (右侧视视角)         (底视足底视角)
```

### 2. 帧对齐聚合调度器核心逻辑
```csharp
public class FrameSynchronizer {
    private readonly ConcurrentDictionary<long, SynchronizedGroup> _pending = new();
    public event Action<SynchronizedGroup> FrameGroupReady;

    public void OnFrameArrived(int camIndex, CameraFrame frame) {
        var group = _pending.GetOrAdd(frame.HardwareFrameId, id => new SynchronizedGroup(id));
        group.Add(camIndex, frame);
        if (group.IsComplete(totalCameras: 3)) {
            _pending.TryRemove(frame.HardwareFrameId, out _);
            FrameGroupReady?.Invoke(group);
        }
    }
}
```

### 🛠️ 上位机实战避坑（工程案例）
在三相机步态分析实验中，早期仅使用系统时间 `DateTime.Now` 匹配多相机图像，由于 Windows 调度抖动（误差 15ms），导致左脚着地画面与右侧脚悬空画面匹配在一起，空间 3D 重建彻底失真。改为硬件 Line0 硬外触发 + 相机硬件纳秒时间戳校验后，三台相机曝光时间差严格控制在 5 微秒以内，三维步态重构误差小于 0.2mm。

### ⚠️ 常见连环追问
- Q: 若其中一台相机偶然丢了一帧，聚合器会导致后续所有帧都卡死等待吗？（答：不会，聚合器挂载定时清理定时器，超过 20ms 未收齐的帧组被标记为缺陷帧强制清理，绝不阻塞后续帧）

## 6. 为什么高帧率（120 FPS）多相机测控场景下软件触发同步不可行？IEEE 1588 PTP 协议与硬件 TTL 外触发的深度对比

- **题目标识**：`VIS-06`
- **重要程度**：⭐⭐⭐⭐⭐ (5星)
- **核心标签**：`软件触发局限` `IEEE 1588 PTP` `TTL硬触发` `时间对齐精度`

### 💡 30秒速记提纲（面试张口就来）
> 1. **软件触发致命死穴**：网络协议栈传输延迟（GVCP 报文单次 1~5ms 抖动）+ Windows 非实时操作系统线程调度抖动（10~15ms 时间片）。在 120 FPS（周期 8.33ms）下，三台相机软触发离散度甚至大于一个完整帧周期，无法实现有效时间对齐。
> 2. **IEEE 1588 PTP 协议机制**：基于以太网硬件时间戳的精密时钟同步协议，通过主从时钟交换报文消除网络抖动，能将多相机时钟对齐至亚微秒级（< 1μs）；通过 GigE Vision 的 `Action Command` 广播定时触发曝光。
> 3. **实战选型权衡**：硬件 TTL 外触发最可靠、成本低、抗网络干扰强，是工控高帧率首选；PTP 适合远距离无走线条件的大型分布式多相机系统（需交换机与网卡支持 PTP 硬件时间戳）。

### 🔍 深入原理解析
### 1. 三种同步机制全景对比表
| 维度 | 软件触发 (Software Trigger) | IEEE 1588 PTP + Action Command | 硬件 TTL/Strobe 硬触发 |
| :--- | :--- | :--- | :--- |
| **同步精度** | 5ms ~ 20ms（完全失真） | 1μs ~ 10μs（微秒级） | **< 1μs（纳秒级物理响应）** |
| **适用帧率** | < 10 FPS 低速离散检测 | 60 ~ 120 FPS 分布式 | **120 ~ 1000+ FPS 极速测控** |
| **布线复杂度** | 仅网线 | 仅网线（需支持 PTP 的千兆交换机） | 需额外部署 GPIO 航空插头屏蔽线 |
| **操作系统依赖** | 强依赖 Windows 线程调度 | 无依赖（相机硬件解析时钟） | 纯物理电平跳变，完全独立于 OS |

### 🛠️ 上位机实战避坑（工程案例）
某视觉项目试图通过 C# 发送 `MV_CC_SetCommandValue("TriggerSoftware")` 循环触发 3 台千兆网相机，发现无论怎么优化 Task 调度，三台相机捕获的运动物体位移均有明显错位。现场直接改接 GPIO 航插硬线：由伺服控制器的 OC 门输出 120Hz 脉冲经高速光耦隔离后直连 3 台相机 Line0，当天彻底解决位移错乱问题。

### ⚠️ 常见连环追问
- Q: PTP 同步中 Master 相机是怎么选出来的？（答：通过最佳主时钟算法 BMCA 自动竞选，或上位机指定网卡/主相机为固定 Master）

## 7. 工业千兆网（GigE）工业相机 120 FPS 高帧率极速吞吐下，全链路 0 丢帧的架构设计与网卡驱动参数调优

## 10. C# 工业上位机中 AI 视觉算法的最佳集成架构：ONNX Runtime 原生嵌入 vs 多进程 IPC 隔离深度权衡

- **题目标识**：`VIS-10`
- **重要程度**：⭐⭐⭐⭐⭐ (5星)
- **核心标签**：`AI视觉集成` `ONNX Runtime` `多进程隔离` `IPC` `共享内存`

### 💡 30秒速记提纲（面试张口就来）
> 1. **主流两大流派**：
>    - **流派 A（ONNX Runtime 原生同进程嵌入）**：算法导出为 ONNX，C# 引用官方 NuGet 库直接跑，内存零拷贝直灌 Tensor，性能极致、部署单一，适合工业已定型轻量模型；
>    - **流派 B（独立进程物理隔离）**：算法在独立 Python/C++ 守护进程中跑，通过**共享内存（MemoryMappedFile）**传递图像、命名管道传递结果，实现物理级容灾崩溃隔离。
> 2. **工程防崩溃考量**：第三方 Python/C++ 深度学习库（如 PyTorch、CUDA 驱动）极易发生底层段错误（Access Violation），非托管崩溃会导致宿主 C# 进程直接闪退且无法用 try-catch 捕获。稳定性要求极高的 7x24 小时产线强烈推荐**多进程 IPC 隔离**。

### 🔍 深入原理解析
### 1. 两大方案多维权衡
| 维度 | ONNX Runtime 同进程嵌入 | 独立守护进程 IPC 隔离 (MemoryMappedFile) |
| :--- | :--- | :--- |
| **推理延迟** | 极低（直接共享 Native 指针，零拷贝） | 极低（共享内存传递仅几十微秒，几乎无额外拷贝） |
| **内存开销** | 较小（单进程资源共享） | 稍大（需维护两套进程与通信管道） |
| **容灾与稳定性**| 风险高：C++ 底层崩则整个上位机主程序闪退 | **极高：算法崩溃主界面不闪退，1秒内自动拉起重启** |
| **依赖与部署** | 简单（仅需几颗官方 DLL） | 需管理子进程生命周期与心跳保活 |

### 🛠️ 上位机实战避坑（工程案例）
在步态分析与足底压力综合测控系统中：早期采用 Python 脚本通过 Python.NET 进程内互操作，因 Python GIL 锁与 CUDA 显存碎片偶发内存越界，导致操作员测试录制中途软件直接闪退，丢失实验数据。重构为“独立算法守护进程”：主 WPF 上位机负责设备采流与界面交互，通过 `MemoryMappedFile` 开辟 64MB 环形图像共享内存，子进程读取推理并经由命名管道回传关键点坐标。整机上线后再无任何因算法引发的闪退事故。

## 11. OpenCvSharp 在工业上位机视觉开发中的核心要点与非托管内存泄漏防范（Mat Dispose、ROI无拷贝、内存复用）

- **题目标识**：`VIS-11`
- **重要程度**：⭐⭐⭐⭐⭐ (5星)
- **核心标签**：`OpenCvSharp` `非托管内存泄漏` `Mat生命周期` `ROI` `缓冲区复用`

### 💡 30秒速记提纲（面试张口就来）
> 1. **非托管内存失控本因**：`OpenCvSharp.Mat` 内部仅是一个微型 C# 句柄，底层 C++ `cv::Mat` 图像数据分配在非托管堆。**C# GC 只能看到几十字节的托管壳，根本感知不到数兆字节的图像内存**，依赖 GC 终结器必然导致非托管内存暴涨 OOM。
> 2. **四大黄金法则**：
>    - 临时 Mat 必须使用 `using` 或显式 `.Dispose()`；
>    - 循环算法严禁链式调用未解引用的中间产物；
>    - ROI 区域裁剪利用 `new Mat(src, rect)` 头拷贝指针共享，避免无意义的 `.Clone()` 全图深拷贝；
>    - 高频算子输入输出复用预分配好的全局工作 `Mat` 缓冲区。

### 🔍 深入原理解析
### 1. 致命泄漏反面教材与标准示范
```csharp
// 致命错误：链式调用产生 2 个未释放的中间临时非托管 Mat
var edges = src.CvtColor(ColorConversionCodes.BGR2GRAY).Canny(50, 150);

// 工业标准写法：全局复用中间 Mat 实例
private readonly Mat _grayMat = new();
private readonly Mat _edgeMat = new();

public void Process(Mat src) {
    Cv2.CvtColor(src, _grayMat, ColorConversionCodes.BGR2GRAY);
    Cv2.Canny(_grayMat, _edgeMat, 50, 150);
    // 处理 _edgeMat，无需频繁创建与释放
}
```

### 🛠️ 上位机实战避坑（工程案例）
在连续足印形态学跟踪模块中，系统连续运行 2 小时后工控机内存占用从 2GB 飙升至 16GB 最终报 `OutOfMemoryException`。排查发现工程师在找轮廓方法内部调用了 `Cv2.FindContours`，中间创建了数百个临时 `Mat` 未做 Dispose。重构为“工作缓冲区池化”并严守 `using` 规约后，系统 7x24 小时长时间运行，内存曲线平滑稳定在 1.8GB，无任何泄漏波动。

## 13. OpenCV 与 WPF 图像交互深度避坑：Mat 转 WPF WriteableBitmap 零拷贝渲染、跨线程限制与 Stride 对齐

- **题目标识**：`VIS-13`
- **重要程度**：⭐⭐⭐⭐⭐ (5星)
- **核心标签**：`OpenCV与WPF` `WriteableBitmap` `跨线程更新` `内存对齐` `Stride`

### 💡 30秒速记提纲（面试张口就来）
> 1. **为什么不能用 ToBitmapSource()**：其内部每次都申请全新的托管内存并进行全图深拷贝，高帧率下每秒产生几百兆大对象堆垃圾，直接触发 GC 停顿与界面肉眼可见的卡死。
> 2. **WriteableBitmap 零拷贝机制**：初始化单例 `WriteableBitmap`，更新时调用 `Lock()` 获取非托管显存首地址 `BackBuffer`，直接利用 `Buffer.MemoryCopy` 将 Mat 数据指针拷入，标记脏矩形 `AddDirtyRect` 后 `Unlock()`。
> 3. **两大深水区避坑**：
>    - **跨线程所有权**：WriteableBitmap 具有 UI 线程亲和性，后台图像处理完成后，通过 `Dispatcher.BeginInvoke` 写入，或前台挂载 `CompositionTarget.Rendering` 节拍器主动去后台共享指针拉取；
>    - **Stride 步长与颜色通道**：OpenCV 是 BGR 排布，WPF 是 `Bgr24`；且宽度不是 4 的倍数时必须做行跨度对齐（Stride Alignment），否则图像发生斜向撕裂。

### 🔍 深入原理解析
### 1. 极致高效渲染代码模板
```csharp
public unsafe void RenderMatToWriteableBitmap(Mat mat, WriteableBitmap targetBmp) {
    if (targetBmp.Dispatcher.CheckAccess()) {
        UpdateInternal(mat, targetBmp);
    } else {
        targetBmp.Dispatcher.BeginInvoke(() => UpdateInternal(mat, targetBmp), DispatcherPriority.Render);
    }
}

private unsafe void UpdateInternal(Mat mat, WriteableBitmap bmp) {
    bmp.Lock();
    // 直接内存拷贝，0 堆内存分配
    Buffer.MemoryCopy(mat.DataPointer, bmp.BackBuffer.ToPointer(), 
                      mat.Total() * mat.ElemSize(), mat.Total() * mat.ElemSize());
    bmp.AddDirtyRect(new Int32Rect(0, 0, mat.Width, mat.Height));
    bmp.Unlock();
}
```

### 🛠️ 上位机实战避坑（工程案例）
在双目相机 1280x1024 预览界面开发中，初期界面只要放大或调节曝光就偶发画面错位成一道道斜纹黑白乱码。排查发现当裁剪 ROI 宽度为奇数（如 801 像素）时，OpenCV 单行字节数为 $801 \times 3 = 2403$，不满足 Windows 图像 4 字节对其要求。在更新函数中严格加入 `int stride = (width * 3 + 3) & ~3;` 并使用 `Mat.Step` 对齐拷贝后，彻底杜绝了图像错位撕裂问题。

### ⚠️ 常见连环追问
- Q: WriteableBitmap 在高刷新率下会产生撕裂吗？（答：不会，WriteableBitmap 的 Lock/Unlock 与 AddDirtyRect 深度整合在 WPF 的 DirectX 双缓冲渲染管线中，由 DWM 窗口桌面管理器统一进行垂直同步同步合成）
